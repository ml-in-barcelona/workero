# Development

`make help` lists the targets. Run `make build` to build the library, CLI, and
examples. Run `make fmt` to format the code, and `make test` to run the unit,
worker, worker-init, worker-exports, and CLI tests.

## Tests

- Unit tests in `test/unit/` are alcotest executables built with `(modes js)`
  and run by Node through `dune test` (`make test-unit`). They cover code that
  does not await, such as `Workero.URL`. Alcotest has no wasm runtime, and Node
  22 has no JSPI, so code that uses `Promise.await` cannot run here. To add a
  test, write a function in `test/unit/test_workero.ml` and list it in
  `Alcotest.run`. A new file needs its own `(test (name ...) (modules ...)
  (modes js) (libraries workero alcotest))` stanza.
- Worker tests in `test/worker/` run with `make test-worker`. This builds
  `test/worker/main.ml` with `workero build` and runs `test/worker/tests.mjs`
  in `workerd test` without a port. The worker is bound as `env.WORKER`, with
  `GREETING` set. To add a test, add a route to `test/worker/main.ml` and a
  case to `cases` in `tests.mjs`. Check `status`, `body`, `headers`, or `throws`
  for a handler that raises. A service binding rethrows where HTTP answers
  500. `workerd` must be on `PATH`; `opam install workerd`, `npm install workerd`
  or `wrangler` provides it. KV, R2, and Cache bindings point at small JS services in
  `test/worker/services/`. D1 is a `wrapped` binding over SQLite there.
- Init tests in `test/worker-init/` run with `make test-worker-init`. They load
  a worker whose toplevel raises and expect the load to fail with the OCaml
  exception.
- Worker export tests in `test/worker-exports/` run with
  `make test-worker-exports`. They check which handlers each worker exports.
- CLI tests in `test/cli/` run with `make test-cli`. They check `workero build`
  and `workero package`, including arguments, output, and errors. Fixtures
  with missing wasm implementations must fail to build, with and without
  `--pretty`, unless `--allow-missing-primitives` is set.

## Documentation

Edit library API descriptions in the `.mli` files and guides in `doc/*.mld`.
The docs of `workerd` and `wrangler` are `doc/workerd/index.mld` and
`doc/wrangler/index.mld`. Run `make docs` to generate HTML and Markdown with
odoc; it copies Markdown to `docs/`. Do not edit generated `docs/` pages directly.

## Releasing workero

Add the changes to `CHANGES.md` and push a tag such as `1.0.0` or `v1.0.0`.
`ci.yml` releases `workero` with `dune-release` on these tags only.

## Releasing workerd and wrangler

The opam packages `workerd` and `wrangler` have their own version, changelog
(`CHANGES-workerd.md`, `CHANGES-wrangler.md`) and tag. Their opam files are at
the repository root, next to `workero.opam`, and each has a `(package)` stanza
in `dune-project`.

- `workerd.opam` installs the prebuilt workerd binary. The version is the
  version of the npm package `workerd`. opam cannot filter a download by
  platform, so the file lists the four npm tarballs of
  `@cloudflare/workerd-<platform>` as `extra-source` (about 154 MiB), and a
  command filtered by `os` and `arch` unpacks one.
- `wrangler.opam` installs a bundle of wrangler. The version is the version of
  the npm package `wrangler`. It depends on the exact workerd version that
  wrangler pins.

The opam files are generated by dune from `dune-project` and from
`<package>.opam.template`. A template field replaces the field that dune would
generate: the templates set `version`, `available`, `depends`, `build`,
`install` and `url`, so the files have no `dune` dependency and no dune build
step. Do not edit the `.opam` files or the templates by hand. The scripts in
`scripts/` write the templates:

- `node scripts/workerd-opam.ts <version>` fetches the npm metadata of the four
  platform packages of workerd.
- `node scripts/wrangler-opam.ts <version>` fetches the npm metadata of
  wrangler and the workerd version that it pins.
- `node scripts/changelog.ts <workerd|wrangler> <version> "<note>"` adds a
  `## <version>` section to the changelog. Text under `## Unreleased` becomes
  the section; the note is the default.

Then run `opam exec -- dune build @install --auto-promote` to update the `.opam`
files. `dune build @install` fails when they are out of date, and CI runs it.
Node.js 22.18 or later runs the scripts.

### Automatic releases

Two workflows run every day and on request: `sync-workerd.yml` at 05:17 UTC
and `sync-wrangler.yml` at 05:47 UTC. They need the secret `GH_TOKEN`: a token
that can push to `main` and to tags, and start workflows. Both use the
concurrency group `sync-upstream`, so they never run at the same time. Each run:

1. Reads the npm registry (`scripts/upstream.ts <package>`).
   - `sync-workerd` takes the `workerd` version that the latest `wrangler`
     pins. Other workerd versions are not released: npm has a new workerd
     almost every day.
   - `sync-wrangler` takes the latest `wrangler`. It skips when the tag
     `workerd-<pinned version>` does not exist. A later run releases it.
2. Does nothing when the version already has a tag. Otherwise
   `scripts/release-upstream.sh <package>` writes the template and the
   changelog section, regenerates the opam files with dune, runs `opam lint`,
   commits, and makes the tag `workerd-<version>` or `wrangler-<version>`.
3. Pushes the commit and the tag in one atomic push. When another commit
   reached `main` first, the job rebases, moves the tag, and tries again, up
   to three times. When it still fails, nothing is published, and the next run
   starts again.

Only the latest versions are released. Versions that npm published between two
runs are skipped.

The push uses `GH_TOKEN`, not the default `GITHUB_TOKEN`. A tag that
`GITHUB_TOKEN` pushes does not start other workflows. With `GH_TOKEN`, the tag
starts `release-binaries.yml` as for a manual tag, and the push to `main`
starts CI. The release job needs `GH_TOKEN` anyway, to push to the
`opam-repository` fork.

Re-runs are safe. A version with a tag is not released again. At the start of a
run, `scripts/restart-releases.sh <package>` starts `release-binaries.yml`
again for the latest version that has a tag but no successful or active release
run. `release-binaries.yml` reuses an existing GitHub release and an existing
pull request. The wrangler pull request on `opam-repository` can fail its
checks until the pull request of the workerd version that it needs is merged.

### Manual releases

To release by hand, run the scripts above, commit, and push the tag
`workerd-<version>` or `wrangler-<version>`. To retry a release, run
`release-binaries.yml` from the Actions tab with the tag.

`release-binaries.yml` makes a GitHub release with the changes of that version,
and opens a pull request on `ocaml/opam-repository` from your fork. For
wrangler, it builds the bundle first (`scripts/wrangler-bundle.ts`), attaches it
to the release, and uses it as the `url` of the opam file. `dune-release` does
not release these packages: it sets the `url` to a tarball of this repository,
and `davesnx/dune-release-action` reads the whole tag as the version. The
`workero` release step passes `packages: workero`, so `dune-release` ignores the
other opam files; without `-p`, it lints every root opam file.
